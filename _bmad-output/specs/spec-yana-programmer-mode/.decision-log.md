## 2026-06-13 — Update: CAP-3 architectural revision (methodology artifacts in git)

Reason: if YANA runs BMAD/SpecKit outside the engine, generated files (SPEC.md, PRD, stories) land outside the worktree and never reach the git history. ## 2026-06-13 — Update: open question resolutions from Fred

**OQ resolved — Worktree ownership:** YANA manages the git worktree lifecycle. One YANA programmer session = one worktree. Engine operates within the worktree YANA provides. Hardened isolation tracked in issue #3. Added as constraint.

**OQ resolved — Decision-point filter:** YANA defines the filter (not configurable per repo) in this version. Added as constraint.

**OQ updated — Engine selection:** "PI" was a placeholder; alternatives were not evaluated in the brainstorm. Renamed to "coding engine" throughout. Open question rewritten to make engine selection explicit as the blocking decision for CAP-1.

**OQ resolved — Clarification override (CAP-2):** No override exists. If Fred does not clarify, the process stops. YANA does not proceed with unresolved ambiguity — same as how a human engineer behaves when they don't get an answer. CAP-2 success criterion updated. Question closed.

**OQ resolved — Engine selection and integration architecture:** Claude Code is the initial engine. Architecture must be modular and configurable from the start — same pattern as existing `providers.py`/`providers.yaml`. Engine declared in config, not hardcoded. Constraint updated.

**OQ resolved — Integration protocol (researched 2026-06-13):** Claude Code exposes two programmatic interfaces: (1) Agent SDK (Python/TypeScript) — no subprocess overhead, multi-turn via `--resume`, structured outputs via `--json-schema`; (2) subprocess `claude -p` — 3–5s startup per call, better for one-shot tasks. Claude Code is NOT an MCP server (it consumes MCP, doesn't expose one). Decision: Agent SDK as primary integration, subprocess as fallback. Added to Assumptions. All open questions resolved.
